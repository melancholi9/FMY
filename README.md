# FMY

## 通信速度ボトルネック分析レポート

**調査日:** 2026-02-24
**対象環境:** Linux 4.4.0 (仮想コンテナ環境)
**ネットワークIF:** `66d8e5cba4-v` (仮想インターフェース)

---

## 特定されたボトルネック

### 1. TCPの輻輳制御アルゴリズムが古い (`reno`)

| 項目 | 現在の設定 | 推奨 |
|------|----------|------|
| `tcp_congestion_control` | `reno` | `cubic` または `bbr` |

**問題:** TCP Renoは1980年代に設計された古いアルゴリズムで、パケットロスが発生した際にウィンドウサイズを半減させる。高レイテンシ・高帯域幅環境ではスループットが大幅に低下する。

**影響度:** 高

---

### 2. ソケットバッファ上限が小さい

| パラメータ | 現在値 | 備考 |
|-----------|--------|------|
| `net.core.rmem_max` | 212,992 bytes (~208 KB) | 受信バッファ上限 |
| `net.core.wmem_max` | 212,992 bytes (~208 KB) | 送信バッファ上限 |
| `net.ipv4.tcp_rmem` (max) | 4,194,304 bytes (4 MB) | TCPが要求できる最大値 |
| `net.ipv4.tcp_wmem` (max) | 4,194,304 bytes (4 MB) | TCPが要求できる最大値 |

**問題:** `rmem_max`/`wmem_max` が 208 KB に制限されているため、TCPが4MBのバッファを要求しても上限でキャップされる。帯域幅遅延積 (BDP = 帯域幅 × 往復遅延) が大きい場合にウィンドウが詰まりスループットが落ちる。

**影響度:** 中〜高

---

### 3. TCP最小再送タイムアウト (RtoMin) が200msと大きい

| パラメータ | 現在値 |
|-----------|--------|
| `RtoMin` | 200 ms |
| `RtoMax` | 120,000 ms (120秒) |

**問題:** パケットロスが発生した場合、最小でも200ms待ってから再送する。データセンター内など低レイテンシ環境では過剰に長い。

**影響度:** 低〜中

---

### 4. 多数の短命コネクション (コネクションチャーン)

| 指標 | 値 |
|------|----|
| `ActiveOpens` (総接続数) | 364 |
| `CurrEstab` (現在確立中) | 5 |

**問題:** 多くの接続がオープン後すぐにクローズされている。TCPの3ウェイハンドシェイク・スロースタートのオーバーヘッドが毎回発生し、短いリクエストでは実効スループットが低下する。HTTP Keep-Aliveや接続プールが未活用の可能性がある。

**影響度:** 中

---

### 5. TCP Fast Open (TFO) が無効

**問題:** TFOが有効化されていない。TFOを使うとSYNパケットにデータを乗せて送れるため、新規接続時の1往復分のレイテンシ (RTT) を削減できる。

**影響度:** 中 (短命コネクションが多い環境では特に効果大)

---

### 6. 仮想ネットワークインターフェースによるオーバーヘッド

**現状:** `66d8e5cba4-v` はコンテナ/仮想環境の仮想NIC。物理NICと比較してCPU処理コストが高い。

**影響度:** 低〜中 (環境依存)

---

## 現状の良い点

- パケットエラー: **0**
- パケットドロップ: **0**
- TCP再送: **0** (RetransSegs=0)
- コリジョン・キャリアエラー: **0**

現時点でのパケットロスや輻輳は発生していない。ボトルネックは主に設定値による理論的上限の制約。

---

## 改善案

```bash
# 1. 輻輳制御アルゴリズムをcubicまたはbbrに変更
sysctl -w net.ipv4.tcp_congestion_control=cubic

# 2. ソケットバッファ上限を拡大
sysctl -w net.core.rmem_max=16777216
sysctl -w net.core.wmem_max=16777216

# 3. TCP Fast Openを有効化 (クライアント+サーバー両方)
sysctl -w net.ipv4.tcp_fastopen=3

# 4. アプリケーション側でコネクションプール/Keep-Aliveを活用
#    (HTTP/2やgRPCへの移行も検討)
```
